# TASK-011 persistence architecture — proposal R1
Status: SA planning only, NOT IMPLEMENTED. All recommendations below AI_PROPOSAL pending Human Architecture Gate. PM Q001/Q003/Q004/Q005 are binding confirmed requirements.

## Boundary and technology
Keep single Core Domain/Application project. Add CloudFileManager.Infrastructure project containing SqliteFileSystemStore and versioned SQL. Web references Core + Infrastructure; Infrastructure references Core.Application contracts; Application references Domain. Domain/Application never reference SQLite or Infrastructure. Runtime call flow outward through a port is NOT source dependency direction.
Recommend direct Microsoft.Data.Sqlite (compatible .NET10 stable package pinned at DEV after approval); parameterized SQL, explicit transaction, no EF/Dapper. Existing tree aggregate is small; full-tree replace per successful mutation gives easily audited atomicity. Cost O(nodes+tags) and full-write amplification accepted for assignment; no performance claims for large trees.

One Application port, IFileSystemStore, with cohesive durable aggregate operations: LoadOrInitialize(seedDocument) -> document + durableRevision; Commit(document, expectedRevision, operationId) -> receipt. Concrete document uses immutable value rows, not live FsNode references or serialized session. Commit errors distinguish ConfirmedNotCommitted from OutcomeUnknown. SQL types/connections/transactions never cross port. No public generic UnitOfWork/IRepository<T>, no per-node repository. A filesystem store is justified by actual durable aggregate boundary and failure injection.
Application FileSystemDocument mapper captures live tree and validates/rehydrates durable rows. Domain internal restoration constructors accept validated supplied IDs; regular builders and Prototype keep generating IDs. Application may call internal constructors within Core; no Infrastructure friend access, public setters, reflection hydration or dependency reversal. Restore tags only through controlled mapper, extend L06 allowlist narrowly for that mapper, retain all six checks and negative controls.

## Lifecycle / ownership
Web-only configured local DB path (proposal: content-root App_Data/filesystem.db, configurable for deployments/tests; exclude DB/journal files from Git). One host/workspace/process and one active application owner per file; acquire lifetime OS-backed sidecar exclusive file lock before loading. Durable revision conditional update detects accidental stale writers; unsupported external edits must not be overwritten silently.
Before accepting HTTP: open store, enable foreign_keys on every connection, validate recognized application/schema version. For truly new/empty uninitialized DB create schema+seed+metadata in one transaction. A versioned DB unexpectedly missing its Root is corruption, not an invitation to reseed. Reject unknown/unversioned tables, unsupported versions, invalid rows, multiple/disconnected roots, cycles or malformed values; no auto-delete/recreate. v1 needs no conversion from historical demonstration SQL; any future version gets explicit migration decision.
Validate document fully and create a detached live root, then initialize actual FileSystemSession.Instance via an explicit persistence-enabled bootstrap overload. Existing Reset(root) remains in-memory and drops prior persistence binding; production bootstrap never invokes Reset during requests. IFileSystemSession consumer surface unchanged. Console still uses Reset(root), existing in-memory constructors/demo, and has no Infrastructure reference or DB access.
Startup transient state clean: empty editing history/clipboard/log/progress/search, Size ASC. Proposal: select original seed path API介面定義.docx when present and a File, otherwise Root (never persist selection). Persisted filesystem is authoritative, not original sample. No shutdown save: each mutation durable on return; shutdown releases resources after in-flight operation completes. Crash loses transient state by design.

## Atomicity: why EditingSession must change
Current Execute mutates then immediately pushes Undo/clears Redo. Public Undo cannot recover those discarded entries, and inverse commands change TreeState.Revision. New internal transaction pipeline in EditingSession must delay history publication and preserve object identity; not a generic facade calling public Undo after Save fails.
1. Under existing WebWorkspace.Gate, validate live membership/version/no-op. No-op, Copy, selection, sorting or Visitor operations do not write DB or alter durable revision.
2. Prepare exact inverse and next history containers BEFORE touching live tree. For a new command retain old Undo/Redo objects and build candidate stacks; for Undo/Redo peek old command and build shifted candidates. Allocate needed rollback capacity up front. Capture tree revision, session revision, clipboard reference (immutable snapshot), and impacted parent/index/tag state. Existing commands have simple reversible mutations; prevalidate/preallocate so no partial command mutation on normal exceptions.
3. Apply command (Undo applies its inverse) to SAME live objects; history/clipboard remain unpublished. Capture immutable durable document. Call store.Commit with expected durable revision and unique operationId, while Gate prevents all production readers/requests observing the intermediate tree.
4. Store uses non-deferred write transaction, compare expected revision, delete node_tag then nodes child-first, insert nodes parent-first with original ordinals, insert tag links, update durable revision/operationId in same transaction. Fixed tag catalog stays. A real SQL failure must explicitly rollback; only report ConfirmedNotCommitted after confirming rollback/outcome. Do not conflate disposed transaction with proven failure classification.
5. Confirmed commit: publish prepared history references and current revisions with non-allocating assignments, then return. Only now WebWorkspace changes selection/match state and adds success logs; Clipboard unchanged by mutations. Returning success before DB commit prohibited.
6. Confirmed rollback: invoke internal inverse on same nodes (Delete->reinsert same subtree/index; Paste->remove new subtree; Tag->prior presence; failed Undo->Execute; failed Redo->Undo). Restore TreeState.Revision AND EditingSession revision to captured values after structural compensation. Keep original undo/redo containers and clipboard untouched. Failed Paste's unpublished clone is discarded; existing identities unchanged. Throw Application persistence error, rendered via existing result.error envelope. No success log; one explicit error diagnostic is allowed and is not domain/history mutation. Selection/highlights/progress remain pre-operation because their successful-mutation updates were never reached.
7. Unexpected inverse failure: mark session faulted and stop serving usable state/edits, preserve evidence; never Reset/reload/clear history as ordinary recovery. Fail-closed host stop proposed for Human approval. Process death cannot preserve in-memory history, but DB transaction remains durable source for next boot.

Commit ambiguity: if provider throws during/after COMMIT or cleanup, read revision+operationId through a fresh connection while exclusive owner lock is held. Matching receipt means committed: finish memory publication, not rollback. Unchanged prior revision after confirmed abort means compensate. Unreadable/unexpected outcome => faulted host, no retry or success claim, no usable divergent state. Cleanup exceptions after known commit must not be mislabeled rollback. HTTP disconnect after known commit does not reverse it; exactly-once network delivery is not claimed and no API idempotency feature added.

No distributed transaction claim: this is a serialized in-process protocol with reversible commands and SQL atomic commit. Fatal OOM/process kill between durable commit and publication requires restart, not a promise of continuing same session. Normal rollback MUST satisfy PM-Q005. No external callback/event before publication. Tests must demonstrate compensation and stack contents, not just counts.
