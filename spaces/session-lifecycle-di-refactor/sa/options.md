# Option comparison R1
All alternatives evaluated before selection; recommendation is AI_PROPOSAL, pending Human approval.

| Dimension | A Preserve GoF Singleton | B Interface + DI-managed Singleton | C Interface + scoped / other lifetime |
|---|---|---|---|
| Production semantics | Existing process-global Root/history and workspace constructor Reset retained unless separately adjusted | One shared session and one workspace per Web host/service provider; same cross-request observable behavior in ordinary single-host deployment | Request scope makes each request new state; a custom browser/user lifetime needs identity/expiry/state registry; explicit host-long scope could retain state |
| Test isolation | Global Reset, serialization, cold-process observation remain; interface wrapper alone cannot isolate | Fresh real instance/root per fixture; separate service providers isolated; no global reset | Fresh scope/session isolated; test scope must match real lifetime; per-request lifetime cannot prove cross-request editing compatibility |
| Mutable ownership | Static global, bootstrap performed by consumer; owners can reset each other | Composition owns runtime lifetime; session owns root/editing; workspace owns projection and Gate | Request/user/custom-scope owner; risk root/history lifetime shorter or longer than workspace |
| ASP.NET behavior | AddSingleton<WebWorkspace> + global instance; two hosts in same process interfere | Both registrations singleton in same container; each host shares state across clients; no scoped dependency captured | Cannot inject scoped session into singleton workspace; making both scoped loses state between Copy and Paste/Undo requests. Scoped != user session |
| Console behavior | Static access from Program and Bonus | One explicit instance per CLI invocation passed to demo; no DI container package necessary | Explicit lifetime around whole invocation works, but no benefit from request-style scope |
| Complexity | Least code change; no testability improvement | One interface, constructor injection, two registrations, lifecycle tests/call-site migration | Request scope superficially simple but incompatible; user lifetime adds identity/security/eviction; host-long manual scope adds disposal machinery with little gain |
| Compatibility | GoF assertions and classic demo preserved | GoF private constructor/static identity replaced by container identity assertion; Reset and product semantics retained; public C# API static consumers must migrate | Product semantics change unless long-lived scope reconstructed; more design work and approval |
| Future SQLite implications (no implementation) | Static state does not solve DB lifetime/transaction/concurrency; hidden shared dependencies would complicate future work | Session interface does not imply persistence; must not later capture scoped DbContext in singleton. Re-evaluate transaction/connection ownership in a separate task | Request-scoped DB work might suit future data operations, but DB scope is not automatically in-memory clipboard/history scope; no Repository designed |
| Appropriate when | Classic GoF mechanism mandatory and isolation cost accepted | Keep current single-host shared demo behavior while isolating tests/hosts | Product explicitly needs independent user sessions, or suitable owner-defined long-lived scope is independently justified |

Transient: creates a new instance per resolution, not per user. Repeated transient resolution can fragment history; a singleton workspace capturing one transient effectively extends that instance to workspace lifetime. Neither is clearer than B here.

Concrete injection alternative to B: injecting a constructible FileSystemSession already removes global coupling and is viable. One interface adds a stable consumer contract and makes accidental concrete/static access detectable, but incurs maintenance and does not itself produce isolation. Real implementations remain the default test dependency; no mandatory mocking. If Human prefers fewer abstractions, concrete injection is a valid alternative requiring design adjustment before DEV.

Recommendation: B, conditional on approval. It solves the observed different-workspace interference while preserving current host-shared behavior. A remains valid if classic Singleton is non-negotiable. C request/user scope is not recommended for this behavior-preserving task.

Lifetime terminology checked against [Microsoft .NET service lifetimes](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection/service-lifetimes): singleton is shared per container, scoped per scope, transient per resolution; scoped services must not be directly captured by singleton services. This reference defines framework lifetime rules, not this project's product decision.
